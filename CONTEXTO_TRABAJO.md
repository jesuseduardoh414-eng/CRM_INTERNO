### Cómo levantar el proyecto

| | Comando | Dónde |
|---|---|---|
| Frontend | `npm install` · `npm run dev` (Vite) · `npm run build` · `npm run lint` | `frontend/` |
| Backend | `npm install` · `npm run dev` (nodemon) · `npm start` | `backend/` |
| Base de datos (**MySQL o PostgreSQL desde el 2026-10-08**; el prefijo de `DATABASE_URL` decide) | MySQL: XAMPP arrancado · `CREATE DATABASE crm_interno CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci`. Postgres/Supabase: `DATABASE_URL=postgresql://...` (en Supabase además `DIRECT_URL`). Luego `npm run db:migrate` · `npm run db:generate` (repetir `db:generate` cada vez que se cambie de base) | `backend/` |
| Copiar los datos entre bases | `npm run db:copiar -- --desde "mysql://..."` o `"postgresql://..."` (el destino es `DATABASE_URL`; `--reemplazar` si ya tiene filas) | `backend/` |

Variables de entorno: `backend/.env.example` y `frontend/.env.example` son la referencia. El frontend solo necesita `VITE_API_URL`. El backend usa `DATABASE_URL` (**`mysql://...` o `postgresql://...`**; en XAMPP `mysql://root:@localhost:3306/crm_interno`; en Supabase el pooler de transacción, puerto 6543, con `?pgbouncer=true`, más `DIRECT_URL` con el pooler de sesión, puerto 5432, para las migraciones), `JWT_SECRET`, `AUTH_ENCRYPTION_KEY`, `FRONTEND_URL`, correo (`EMAIL_*`), Google Calendar (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`), `ADJUNTOS_DIR` / `CONTRATOS_DIR` (archivos en disco) y `BLOB_READ_WRITE_TOKEN` solo para borrar adjuntos antiguos que quedaron en Vercel Blob. `ORIGEN_DATABASE_URL` (o `--desde`) solo la usa el script de copia; `DB_PROVIDER` fuerza el proveedor sin mirar la URL.

> ⚠️ **Las migraciones solo se aplican solas en Render** (`npm run start:render` hace `migrate deploy` antes de arrancar); en Vercel, cPanel y local: `npm run db:migrate` desde `backend/` (nunca `npx prisma` a pelo: el envoltorio `scripts/prisma.js` es el que elige el esquema). Hay **dos carpetas de migraciones**: `prisma/migrations/` (MySQL, 10 desde `20261005120000_init_mysql`) y `prisma/postgres/migrations/` (Postgres, empezada de cero el 2026-10-08: `init` con todo el modelo + RLS). **Cada cambio del modelo necesita las dos** (`db:migrate:dev` para MySQL, `db:migracion:postgres` para Postgres). La Supabase antigua (datos al 2026-10-05, esquema de agosto) ya no se puede migrar hacia adelante: se vacía (`DROP SCHEMA public CASCADE; CREATE SCHEMA public;`) o se crea un proyecto nuevo, y los datos se traen de XAMPP con `db:copiar`.

## 0-ter. Reglas de publicación y base de datos (decidido por el usuario, 2026-08-07)

1. **Nada se publica ni se sube hasta que el usuario lo apruebe explícitamente.** No hacer `commit` ni `push` por iniciativa propia. El repo es `github.com/r4d-26/CRM_RED4`, rama `master`, y **Vercel despliega automáticamente al hacer push** — por eso subir sin permiso equivale a publicar en producción.
2. **No hay base de datos de pruebas.** El usuario decidió trabajar contra **la misma base real** (Supabase en la nube) y aplicar los cambios directo ahí. Se le explicó el riesgo y lo confirmó; no volver a plantearlo.
3. **Consecuencia a tener presente:** el CRM ya desplegado usa esa misma base. Un cambio de estructura se refleja de inmediato en la app en vivo, aunque el código nuevo todavía no se haya publicado.
4. **Por eso, en cambios de estructura, ir en dos tiempos:** primero solo **agregar** (columnas o valores nuevos, sin quitar ni renombrar), que es compatible con el CRM en vivo; y **quitar o renombrar solo después** de publicar el código nuevo. Aplica en especial a la tarea de estados de proyecto (`EN_PAUSA` → `INACTIVO`, quitar `CERRADO`): renombrar de golpe rompería el CRM que la gente está usando.
5. Antes de cualquier cambio de estructura, **avisarle y recomendar respaldo**.

### Trampas ya pisadas (no volver a caer)

- **Popover de Radix dentro del Dialog de Radix: funciona.** Un portal propio, no — se queda sin recibir clics. Por eso `SelectorMultiple` y `FiltrosTareas` usan panel `absolute` y el calendario/hora de `ModalEvento` usan Popover.
- **El scroll de la app no lo lleva `window`**, sino el `div.flex-1.overflow-y-auto` del Layout. `window.scrollTo` no sirve.
- **Un contenedor con `overflow-y: auto` recorta también en horizontal.** Fue lo que cortaba el panel de notificaciones dentro del menú lateral.
- **`overflow-x: auto` computa `overflow-y: auto`.** En el gantt hay que poner `overflowY: hidden` explícito o nombres y barras se desincronizan.
- **Zona horaria: el servidor corre en UTC y `vercel.json` no define `TZ`.** Para cualquier corte de "hoy", usar `rangoDiaMexico` de [fechas.utils.js](backend/src/utils/fechas.utils.js). Ver sección **5-sexies**.
- **Al sobrescribir CSS de una librería que importa su propia hoja** (react-day-picker), no basta repetir su selector: su CSS acaba después en el bundle. Hay que calificar con una clase propia (`.calendario-crm`).
- **Adjuntos**: el modelo `Proyecto` ya tiene relación `adjuntos Adjunto[]`; los archivos van a **Vercel Blob**, no a disco.
- **Plantillas**: los modelos `PlantillaProyecto` y `PlantillaTarea` ya existen en Prisma. DP2 es solo UI.

## 5-sexies. ⚠️ El corte del día estaba mal en producción

`getActividadMiembros` calculaba "hoy" con `setHours(0,0,0,0)`, que usa la zona del servidor. **Vercel corre en UTC y el `vercel.json` no define `TZ`**, así que el día iba de 00:00 a 23:59 UTC = de las **18:00 del día anterior a las 18:00** en hora de México.

Consecuencia real: **toda tarea cerrada después de las 6 de la tarde contaba como del día siguiente**. En una vista cuyo propósito es el progreso diario, eso la vuelve inservible.

Corregido con [fechas.utils.js](backend/src/utils/fechas.utils.js) (`rangoDiaMexico`), que fija el corte donde de verdad cambia el día: `00:00 México = 06:00 UTC`. Verificado con una tarea de las 19:00 hora de México — antes caía fuera del día, ahora cae dentro.

> El mismo error puede estar en otras partes que usan `setHours(0,0,0,0)` o `finDelDia()` para acotar "hoy". Al tocar `agenda.controller` o `usuarios.controller`, revisar si aplica y reusar `rangoDiaMexico`.

**Nuevo endpoint:** `GET /api/stats/actividad-equipo?fecha=YYYY-MM-DD` (solo admin), separado de `/stats/admin` para que cambiar de día no recalcule todo el tablero.

## 5-quinquies. El Gantt del Inicio — lo que de verdad pasaba

> ⚠️ **Corrección a una afirmación previa de este documento:** el Gantt del Inicio y el del detalle de proyecto **NO comparten componente**. `GanttView.jsx` solo se usa en `ProyectoDetallePage`; el Inicio tiene su propio `ProjectTimeline` dentro de `DashboardPage.jsx`. Se pueden trabajar por separado.

**El diagnóstico de "fechas amontonadas" no era el obvio.** Las etiquetas de mes tenían espacio de sobra (rango real de 71 días ≈ 3 meses, ~367 px por mes). Lo que se encimaba eran **las dos etiquetas de fecha de cada barra**: se posicionaban en `left: offset` y `left: offset + ancho − 44px`, así que con la barra típica (~62 px) quedaban una encima de la otra. Ahora hay **una sola etiqueta después de la barra**.

**Los datos son la otra mitad del problema:** 15 de 29 proyectos **no tienen fecha de fin**. `getProjectRange` ahora resuelve el fin en **tres niveles**, y solo marca el último:

| `origenFin` | De dónde sale | Cómo se dibuja |
|---|---|---|
| `real` | `fechaFin` capturada | barra normal |
| `deducida` | último `completadoEn` de sus tareas | barra normal + nota "según último cierre" |
| `estimada` | nada; se inventan 7 días | **barra rayada** + "estimado" |

El backend expone `ultimaTareaCompletadaEn` en `GET /api/proyectos` (se calcula del array de tareas que ya cargaba, sin consulta extra). Con los datos al 2026-08-07: 14 reales, **4 deducidas** (Dafne pasó de 7 días inventados a 70 reales; ServMaq24 a 67; EREN a 29) y 11 siguen estimadas por no tener ninguna tarea cerrada con fecha.

> Al reescribir `ProjectTimeline` se perdieron los avatares de miembros y el contador de tareas de la columna izquierda. El usuario pidió **devolver solo los avatares** (ahora vía `UserAvatar`, así que muestran foto de perfil; antes dibujaban la inicial a mano). El contador de tareas se dejó fuera a propósito.

**Zona horaria en el conteo mensual:** la columna `"completadoEn"` es `timestamp without time zone` en UTC. Agrupar por mes sin ajustar movía **23 tareas entre junio y julio**. La consulta resta `interval '6 hours'` antes de truncar, siguiendo el `OFFSET_MEXICO_MS` que ya usaba el resto del código.

**104 tareas terminadas no tienen fecha de cierre** y no se pueden ubicar en ningún mes. Se devuelven aparte en `actividadPorMes.sinFecha` y la vista lo dice, en vez de repartirlas o inventarles fecha.

### ⚠️ La primera versión salía con la página 1 casi en blanco

Cada bloque de persona llevaba `break-inside: avoid`. Quien tenía **89 tareas cerradas** no cabía en una hoja, así que el navegador empujaba el bloque completo a la página siguiente y la primera quedaba solo con el título.

La corrección fue **quitar esa regla** y proteger únicamente lo que no debe partirse: una fila (`tr`) y una cabecera respecto de sus filas. Además la ficha de la persona se metió en el **`<thead>`** con `display: table-header-group`, así el navegador la repite arriba de cada página y una lista larga sigue diciendo de quién es.

> Verificado con Chrome sin interfaz sobre un reporte de 89 tareas: la página 1 pasó de **28 a 203 bloques de texto** y el documento de **4 páginas a 3**. Es la forma de comprobar un cambio de impresión sin abrir el navegador a mano.

**El reporte se imprime en papel blanco con tinta negra a propósito** — los colores fijos de `ESTILOS` no son un descuido de la regla de variables CSS: aquí no aplica el tema de la aplicación.

## 5-octies. Borrado múltiple de tareas

Hecho el **2026-08-10**. Un botón *Seleccionar* junto a los filtros enciende el modo selección en la vista de lista **y** en el Kanban: aparece una casilla en cada tarjeta y una barra fija ofrece todas / ninguna / eliminar.

`POST /api/tareas/eliminar-multiples` con `{ ids: [...] }`. Detalles que importan:

- **Cada tarea pasa por el mismo permiso que el borrado suelto.** Las que el usuario no puede tocar **se omiten y se informan** (`{ eliminadas, omitidas }`) en vez de tumbar el lote entero. Una sola tarea prohibida no debe hundir la operación.
- Los `ids` se **deduplican** y hay tope de **200** por llamada.
- La cascada que desvincula dependencias y notificaciones y borra comentarios, adjuntos y bitácora **se reescribió para operar sobre conjuntos** (`borrarTareasEnCascada(tx, ids)`) y ahora la comparten los dos caminos de borrado, el suelto y el masivo.
- En la bitácora se escribe **un apunte por proyecto, no uno por tarea**: el registro sirve para saber qué pasó, no para dejar treinta líneas casi idénticas.

**De paso: la tarea nueva se asigna a quien la crea.** Antes, crear una tarea sin elegir responsable la dejaba sin asignar, pero el panel de actividad **sí la contaba** para quien la creó — la tarjeta y los totales se contradecían. Ahora se asigna al creador, **pero solo si es miembro del proyecto**: el selector de responsables solo ofrece miembros, así que a alguien de fuera lo habría descartado la siguiente edición.

> Verificado con un cliente de Prisma simulado, **sin tocar la base real**: 17 comprobaciones sobre el responsable por defecto (creador miembro / admin / admin de área) y sobre el filtrado de permisos, la deduplicación de ids, el tope del lote y los caminos de error.

## 5-quater. Paginación y filtros en la API

Utilidad compartida: [backend/src/utils/paginacion.utils.js](backend/src/utils/paginacion.utils.js).

> **Regla de oro: si la petición no manda `page` ni `limit`, la respuesta sale completa y SIN el campo `meta`, exactamente como antes.** Es lo que permite desplegar esto sin tocar el frontend ya publicado. Al adoptar la paginación en una pantalla, hay que empezar a leer `meta`.

| Endpoint | Filtros | Límite por defecto |
|---|---|---|
| `GET /api/proyectos` | `q` (nombre, descripción) · `estado` (acepta nombres viejos) | 20 |
| `GET /api/proyectos/:id/tareas` | `q` (título, descripción) · `estado` · `prioridad` | 25 |
| `GET /api/usuarios` | `q` (nombre, email) · `area` · `rol` · `estado` | 10 |

Forma de `meta`: `{ page, limit, total, totalPages, hasNext, hasPrev }`. El `limit` se topa en 100.

**Detalles que no son obvios:**
- **Se pagina en memoria a propósito.** El orden de proyectos y tareas depende de valores que se calculan *después* de la consulta (progreso, rango de estado), así que cortar en la base daría páginas mal armadas. Los *filtros* sí bajan a la consulta, que es lo que reduce el volumen.
- En `tareas`, los filtros solo recortan la lista `tareas`. Los contadores de `progreso` salen de otra consulta sin filtrar y **deben seguir así**, o el porcentaje del proyecto cambiaría al buscar.
- En `usuarios` hay una **caché de 30 s** de la lista completa. Solo se usa y se rellena cuando no hay filtros; guardar un resultado filtrado dejaría datos incompletos para la siguiente petición sin filtros.

Pruebas: `scratchpad/probar-paginacion.mjs` (22 casos de la utilidad) y `scratchpad/probar-endpoints.mjs` (14 casos contra la base real, incluida la compatibilidad hacia atrás).
